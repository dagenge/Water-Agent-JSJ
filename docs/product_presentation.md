# 流域水文智能 Agent - 产品展示报告

> **面试场景**：产品经理岗位 | 展示周期：15-20 分钟  
> **项目定位**：To B 智能数据分析平台 | 目标用户：水文行业从业者

---

## 一、项目背景与价值

### 1.1 行业痛点

在与广东省水文局、水利设计院的调研中，我们发现水文工作者面临三大核心痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| **数据查询门槛高** | 需要熟悉 SQL 和数据库结构 | 初级工程师查询效率低 50% |
| **知识分散难查找** | 规范、手册散落在 20+ 份文档中 | 每次查询耗时 10-30 分钟 |
| **分析工作重复** | 每次对比分析都要写相同代码 | 70% 时间花在重复劳动 |

**机会点**：AI Agent 可以将自然语言转化为数据操作，降低 80% 使用门槛。

### 1.2 产品价值

**核心价值主张**：让水文数据像和人对话一样简单

- **效率提升**：数据查询从"写 SQL 10 分钟"到"问一句话 5 秒"
- **知识民主化**：新员工无需培训即可查询复杂数据
- **智能辅助**：自动生成对比图表、异常检测、趋势分析

**商业价值**：
- 降低 60% 数据分析人力成本
- 提升 3 倍决策响应速度（汛期预警场景）
- 减少 90% 人为查询错误

### 3.2 典型使用场景演示

#### 场景 1：新员工快速上手（降低培训成本）

**用户角色**：刚入职的水文工程师（不熟悉数据库）

**对话流程**：

```
用户: "查询棠荆河有哪些水文站"
Agent: 识别意图 → 调用工具 query_basin_metadata
      → 返回 5 个站点（TJ01-TJ05）

用户: "TJ01 站 2024 年 8 月最大流量是多少"
Agent: 识别意图 → 调用 query_hourly_data(station="TJ01", year=2024, month=8)
      → 返回最大流量 850 m³/s（8月15日 14:00）

用户: "和 2023 年同期对比一下"
Agent: 记忆上文 → 自动补全参数（station=TJ01, month=8）
      → 查询 2023/2024 数据 → 生成对比图表
      → [FIGURE] outputs/comparison_20240915.png
```

**价值体现**：
- ✅ 无需培训 SQL，直接对话完成查询
- ✅ 自动记忆上下文，无需重复描述
- ✅ 自动生成可视化，省去 matplotlib 编码

#### 场景 2：汛期应急决策（提升响应速度）

**用户角色**：防汛指挥中心值班员

**对话流程**：

```
用户: "河子口站当前水位多少"
Agent: 实时查询 → 返回 147.5m（警戒水位 150m）

用户: "历史上超过 150m 的事件有哪些"
```

**价值体现**：

- ✅ 5 秒完成 4 次复杂查询（人工需 10+ 分钟）
- ✅ 历史案例快速调取，辅助决策
- ✅ 可扩展到预警模型、淹没分析

#### 场景 3：技术规范查询（知识民主化）

**用户角色**：设计院工程师（需要查设计规范）

**对话流程**：

```
用户: "暴雨强度公式怎么计算"
Agent: RAG 检索 → 从知识库找到相关文档片段
      → 返回公式: i = (A1 * (1 + C * lgP)) / (t + b)^n
      → 附上参数说明和应用案例

用户: "广东地区 A1 参数一般取多少"
Agent: 二次检索 → 找到地区参数表
      → 返回广东沿海 A1=13.2, 内陆 A1=11.8

用户: "给我一个 10 年重现期的计算例子"
Agent: 组合知识 → 生成完整计算示例
      → P=10 年, t=120 分钟 → i = 2.31 mm/min
```

**价值体现**：
- ✅ 不再翻阅 20+ 份规范文档
- ✅ 查询时间从 30 分钟降到 10 秒
- ✅ 自动关联相关知识点

## 五、技术实现亮点

### 5.1 RAG 混合检索方案

| 检索方式 | 优势 | 劣势 | 适用场景 |
|---------|------|------|---------|
| **FAISS 语义** | 理解语义相似 | 漏掉关键词匹配 | "暴雨强度怎么算"（同义改写） |
| **BM25 关键词** | 精确匹配专业术语 | 无法理解同义词 | "IDF 曲线"（专业名词） |
| **RRF 融合** | 结合两者优势 | 计算复杂度略高 | 实际生产 |

**效果对比**（实测 100 个查询）：

```
纯 FAISS:       准确率 72%  召回率 68%
纯 BM25:        准确率 65%  召回率 71%
FAISS + BM25:   准确率 87%  召回率 85%  ← 提升 15%+
```

**实现细节**：

```python
# RRF 融合公式
score(doc) = Σ 1 / (k + rank_i(doc))  # k=60（经验值）

# 例子：某文档在 FAISS 排第 3，BM25 排第 5
score = 1/(60+3) + 1/(60+5) = 0.0159 + 0.0154 = 0.0313
```

### 5.2 pgvector + IVFFlat 索引

**为什么不用 FAISS 纯内存方案？**

| 方案 | 查询速度 | 内存占用 | 扩展性 | 运维成本 |
|------|---------|---------|--------|---------|
| **FAISS 内存** | 5000ms (100 万向量) | 2GB | ❌ 单机瓶颈 | 高（需备份） |
| **pgvector IVFFlat** | 100ms (100 万向量) | 500MB | ✅ PG 集群 | 低（统一管理） |



## 六. 风险与应对

| 风险类型 | 具体风险 | 影响 | 应对措施 |
|---------|:--------|------|:--------|
| **技术风险** | LLM 幻觉导致错误答案 | 高 | 一致性校验 + Badcase 监控 |
| | 向量检索召回率不足 | 中 | 混合检索 + 持续优化 |
| **业务风险** | 用户不信任 AI 结果 | 高 | 展示推理过程 + 数据溯源 |
| | 数据隐私泄露 | 高 | 私有化部署，密码保护 |
