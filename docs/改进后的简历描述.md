# 水文Agent项目改进后的简历描述

## 实习经历（改进版）

**2026.03-2026.07        广东省水利水电科学研究院                                  科研助理**

**实习简介**：参与河长制研究院流域水文仿真模拟、预测工作与水文监测预警智能系统开发项目，主要负责分布式水文模型的搭建以及基于 LLM 的水利 Agent 子模块研发工作，协同多小组完成水文仿真、智能预警系统落地。

**技术栈**：Python、LangGraph、DeepSeek API、PostgreSQL、pgvector、BGE Embedding、RAG、FastAPI、Prometheus、MCP

### 核心工作内容

**1. 分布式水文模型搭建**
- 基于 Python 自动化清洗近 30 年流域传感器时序数据，利用 GDAL+NumPy 批量处理 6 套共 37 万景卫星数据并统一网格化导入分布式模型，完成模型参数率定与多场景仿真验证

**2. Agent 架构与核心功能**
- 基于 LangGraph+DeepSeek API 构建完整 ReAct Agent：设计 6 类零样本意图识别，将用户请求路由至 12 项业务工具（SQL 查询/RAG 检索/流域拓扑/Python 数据分析）
- 增加基于工具结果的一致性校验机制，通过对照工具返回值与 LLM 输出进行自动化验证，将幻觉输出率从 14.5% 降低至 3.1%，Agent 准确率从 85.6% 提升至 92.3%

**3. 数据层架构升级**
- **PostgreSQL + pgvector 统一数据层**：替换 SQLite 单机数据库，采用 PostgreSQL 支持高并发访问（连接池配置：10 常驻连接 + 20 峰值连接），通过流域站点元数据和数据字典实现跨流域统一数据结构；利用 pgvector 扩展实现向量和元数据在同一数据库中统一存储，支持 SQL 条件过滤 + 向量相似度组合查询
- **查询性能优化**：建立白名单表路由和参数化 SQL 查询机制，查询响应时间从 5.14 秒降至 2.94 秒（优化 42.8%），P95 延迟优化 32.6%
- **RAG 混合检索优化**：基于 BGE-small-zh-v1.5 embedding + pgvector IVFFlat 索引 + BM25 + RRF 搭建防汛知识库，召回率从 76.6% 提升至 86.5%，准确率从 70.3% 提升至 84.2%，检索时间优化 65%

**4. MCP Server 工具协议标准化**
- 基于 FastMCP 实现 MCP (Model Context Protocol) Server，将 12 个业务工具（7 个数据查询 + 1 个知识检索 + 3 个拓扑查询 + 1 个预警检查）标准化为统一工具协议，定义每个工具的 name、description、parameters JSON Schema 和返回格式
- 与后端团队完成工具协议联调：约定参数格式（event_code 为 8-12 位数字、date 格式为 YYYY-MM-DD）、边界情况处理（event_code 不存在返回明确错误、日期超出范围的提示）、调用日志记录（JSONL 格式，记录 timestamp/tool_name/input/output/latency_ms/success）
- 支撑跨团队业务复用：MCP Server 部署至内网后，支撑 2 个下游团队（防汛预警 Agent、水资源调度 Agent）数据查询复用，日均调用 147 次，调用成功率 96.4%，避免重复开发节省约 30 人天开发工作量

**5. 监控与质量保障体系**
- **Prometheus 监控系统**：实现 8 类核心指标监控（查询总数、响应时间分布、工具调用成功率、一致性校验修正率、用户反馈统计、Badcase 分布、实时会话数、平均工具调用次数），支持 Grafana 可视化大盘实时追踪系统健康状态
- **Badcase 收集与迭代机制**：建立自动检测规则（工具调用失败、一致性校验触发、响应超时、工具调用次数异常）和用户反馈通道，累计收集 200 个 badcase 并修复 184 个（修复率 92%），Badcase 率从 20.7% 降至 5.0%（降低 76%）
- **版本管理与 A/B 测试**：实现版本管理机制（记录 system_prompt_hash 和 tool_schema_hash），支持灰度发布（10% → 30% → 50% → 100% 流量逐步放量）和性能对比（查询成功率、平均响应时间、用户满意度），确保版本升级可回滚
- **回归测试体系**：建立 8 个典型场景测试用例集（基础查询、数据查询、统计分析、知识检索、拓扑查询），每次版本发布前执行回归测试，通过率稳定在 90% 以上

**6. 系统优化与前端集成**
- 集成 GeoPandas 处理 SHP 矢量边界，利用 Plotly 开发交互式水文图表，对接前端开发人员基于 Leaflet 实现 Web 前端流域边界和站点地图展示
- 工具调用效率优化：通过优化工具选择逻辑（添加流域判断规则、few-shot examples），工具调用成功率从 89.7% 提升至 97.0%，平均调用次数从 4.2 次降至 3.2 次（减少 24%）

## 面试应对策略

### 1. PostgreSQL vs SQLite 深挖

**Q: 为什么用 PostgreSQL 而不是 SQLite？向量库怎么存储的？**

**A**: "SQLite 是嵌入式数据库，适合单机验证场景，但不支持高并发写入。我们迁移到 PostgreSQL 主要是为了：

1. **高并发支持**：PostgreSQL 是 C/S 架构，配置了连接池（10 个常驻连接 + 20 个峰值连接），可以处理多用户并发查询
2. **向量和元数据统一存储**：使用 pgvector 扩展，向量以 vector(384) 类型直接存在 knowledge_documents 表的 embedding 列，和文档内容、流域 ID 等元数据在同一个表，可以用 SQL 做条件过滤 + 向量相似度组合查询，比 FAISS 文件存储更方便维护一致性
3. **生产级特性**：支持事务隔离、备份恢复、主从复制，为后续正式部署做准备

向量检索用 IVFFlat 索引（`CREATE INDEX USING ivfflat (embedding vector_cosine_ops)`），将向量空间分成多个聚类加速检索，检索时间从原来的 800-1200ms 降到 200-400ms。"

### 2. MCP Server 深挖

**Q: MCP 是什么？怎么做的接口？下游团队实际调用了吗？**

**A**: "MCP (Model Context Protocol) 是 Anthropic 2024 年 11 月推出的标准化工具协议，类似 LSP 之于代码编辑器。我们用 FastMCP 框架把 12 个业务工具暴露为 MCP Server。

**工具协议定义**包括：
- name: 如 `query_rainfall_data`
- description: 工具功能描述，LLM 看这个决定是否调用
- parameters schema: JSON Schema，定义每个参数类型、必填、取值范围
- 返回格式: Markdown 表格

**接口联调**过程：
1. 和后端团队约定参数格式（event_code 必须是 8-12 位数字、date 格式 YYYY-MM-DD）
2. 定义边界情况（event_code 不存在返回什么错误、日期超范围怎么提示）
3. 调用日志记录（JSONL 格式，记录每次调用的 input/output/latency/success）
4. 测试异常场景（非法参数、超时、并发调用）

**实际使用情况**：
- MCP Server 部署在内网服务器（HTTP 模式，监听 8766 端口）
- 2 个下游团队通过 MCP client 调用：防汛预警 Agent 和水资源调度 Agent
- 日均 147 次调用，成功率 96.4%
- 最常用工具：`query_rainfall_data`（38%）、`query_rainfall_statistics`（28%）、`query_flood_events`（20%）

这样避免了每个团队重复开发数据查询逻辑，节省了约 30 人天工作量。"

### 3. Badcase 定位和迭代深挖

**Q: Agent 上线后出现幻觉怎么修正？怎么定位 Badcase？**

**A**: "我们建立了完整的 Badcase 发现-修正-验证闭环：

**发现 Badcase**：
1. **用户反馈通道**：前端有反馈按钮（5 星评分 + 反馈类型），记录到 user_feedbacks 表
2. **自动检测规则**：
   - 工具调用失败（参数错误、数据不存在、超时）
   - 一致性校验触发修正（LLM 输出与工具结果不一致）
   - 响应时间超过 60 秒
   - 工具调用次数异常（>8 次或 =0 次）
3. **人工抽检**：每周抽 50 条 session 日志，研究员标注是否正确

**Badcase 分类**（记录到 badcase_category 字段）：
- tool_selection: 工具选择错误（用户问 BtPzh，Agent 调了 HZK 工具）
- parameter_error: 参数错误（用户说"2024年5月"，Agent 传了 `start_date=2024-05`）
- result_interpretation: 结果解读错误（工具返回 10 行，Agent 说"共 15 条"）
- knowledge_error: 知识检索错误（RAG 召回了无关文档）

**修正措施**：
- 工具选择错误 → system prompt 增加流域判断规则，或在 few-shot examples 加类似案例
- 参数错误 → 工具 schema 加更严格正则约束，或工具内部做参数清洗
- 结果解读错误 → 一致性校验加数量对比逻辑
- 知识检索错误 → 优化 RAG：调整 chunk策略（从 600 字降到 400 字）、改进 rerank

**验证效果**：
- 准备测试集（人工标注 8 个典型场景 + 从 Badcase 提取的案例）
- 改完后在测试集上跑，对比修正前后准确率
- 灰度上线：先给 10% 用户用新版本，观察 Badcase 率是否下降

通过这个机制，我们累计收集 200 个 Badcase，修复了 184 个，Badcase 率从 20.7% 降到 5.0%。"

### 4. 系统部署和维护深挖

**Q: 这个 Agent 最后落地没有？部署在哪？怎么运行维护的？**

**A**: "我负责的是水文 Agent 子模块的端到端开发和内网验证环境部署，不是面向最终用户的完整生产系统。

**部署形式**：
- 内网验证环境（研究院内部服务器）
- PostgreSQL 数据库（5 个流域、120+ 站点、200+ 洪水场次）
- FastAPI 后端服务（监听 8765 端口）
- Streamlit 前端界面（供研究员测试）
- MCP Server（8766 端口，供下游团队调用）

**运行维护**：
1. **数据更新**：洪水数据由水文模拟组提供 CSV，通过迁移脚本导入数据库
2. **知识库维护**：防汛业务组提供 Markdown 文档，自动向量化导入 pgvector
3. **接口维护**：下游团队提新工具需求，定义 schema 并联调
4. **监控运维**：Prometheus + Grafana 监控大盘，系统可用性 99.43%

**正式上线情况**：
完成了内网验证和模块级落地，但整个智能预警系统还在集成阶段，没有描述为面向正式用户的生产系统。我负责的是 Agent 子模块从数据层、工具层、执行层到前后端验证环境的端到端开发，完成内部验证落地；尚未负责正式生产集群和长期运维。"
