## 一、项目背景与价值

### 1.1 行业痛点

在与广东省水文局、水利设计院的调研中，我们发现水文工作者面临三大核心痛点：

| 痛点 | 现状 | 影响 |
|------|------|------|
| **数据查询门槛高** | 需要熟悉 SQL 和数据库结构 | 初级工程师查询效率低 50% |
| **知识分散难查找** | 规范、手册散落在 20+ 份文档中 | 每次查询耗时 10-30 分钟 |
| **分析工作重复** | 每次对比分析都要写相同代码 | 70% 时间花在重复劳动 |

**机会点**：AI Agent 可以将自然语言转化为数据操作，降低 80% 使用门槛。

### 1.2 产品价值

**核心价值主张**：让水文数据像和人对话一样简单

- **效率提升**：数据查询从"写 SQL 10 分钟"到"问一句话 5 秒"
- **知识民主化**：新员工无需培训即可查询复杂数据
- **智能辅助**：自动生成对比图表、异常检测、趋势分析

**商业价值**：
- 降低 60% 数据分析人力成本
- 提升 3 倍决策响应速度（汛期预警场景）
- 减少 90% 人为查询错误

## 六、技术实现亮点

### 6.1 RAG 混合检索方案

**为什么不用纯向量检索？**

| 检索方式 | 优势 | 劣势 | 适用场景 |
|---------|------|------|---------|
| **FAISS 语义** | 理解语义相似 | 漏掉关键词匹配 | "暴雨强度怎么算"（同义改写） |
| **BM25 关键词** | 精确匹配专业术语 | 无法理解同义词 | "IDF 曲线"（专业名词） |
| **RRF 融合** | 结合两者优势 | 计算复杂度略高 | 实际生产 |

**效果对比**（实测 100 个查询）：

```
纯 FAISS:       准确率 72%  召回率 68%
纯 BM25:        准确率 65%  召回率 71%
FAISS + BM25:   准确率 87%  召回率 85%  ← 提升 15%+
```

**实现细节**：
```python
# RRF 融合公式
score(doc) = Σ 1 / (k + rank_i(doc))  # k=60（经验值）

# 例子：某文档在 FAISS 排第 3，BM25 排第 5
score = 1/(60+3) + 1/(60+5) = 0.0159 + 0.0154 = 0.0313
```

### 6.2 pgvector + IVFFlat 索引

**为什么不用 FAISS 纯内存方案？**

| 方案 | 查询速度 | 内存占用 | 扩展性 | 运维成本 |
|------|---------|---------|--------|---------|
| **FAISS 内存** | 5000ms (100 万向量) | 2GB | ❌ 单机瓶颈 | 高（需备份） |
| **pgvector IVFFlat** | 100ms (100 万向量) | 500MB | ✅ PG 集群 | 低（统一管理） |

**IVFFlat 原理**（聚类加速）：
```
1. 离线：K-Means 将 100 万向量聚成 100 类（lists=100）
2. 在线：查询时只搜最近的 10 个类（probes=10）
3. 复杂度：O(100 + 100万/10) = O(10100) vs 暴力 O(100万)
```

**参数调优**：
- `lists = sqrt(N)`：100 万向量 → lists=1000
- `probes = lists * 0.1`：probes=100（召回率 95%+）

### 6.3 LangGraph 状态管理

**为什么不用 LangChain 原生？**

LangChain 的 `ConversationChain` 是无状态的，每次对话需要传入完整历史：
```python
# LangChain 原生（❌ 无持久化）
chain.run(input="查询流量", history=[msg1, msg2, ...])
```

LangGraph 提供 `MemorySaver`，自动持久化到数据库：
```python
# LangGraph（✅ 自动持久化）
memory = MemorySaver()
graph = create_react_agent(llm, tools, checkpointer=memory)
graph.invoke(input, config={"session_id": "user123"})
```

**优势**：
- ✅ 多轮对话自动记忆（无需手动传历史）
- ✅ 会话可恢复（服务重启后继续对话）
- ✅ 支持分支回滚（撤销上一步操作）

## 八、面试 Q&A 预演

### Q1: "你们和 ChatGPT 的差异是什么？"

**回答思路**：

"我们的核心差异在于**领域专业性**和**生产可用性**：

1. **领域知识**：我们内置了 500+ 页水文规范和历史案例，ChatGPT 需要每次用 Prompt 补充背景，且容易遗漏专业细节。比如'暴雨强度公式'，ChatGPT 会给通用公式，但我们直接给出广东地区的参数和应用案例。

2. **数据安全**：政府单位有数据不出域的要求，我们支持私有化部署，所有数据都在客户内网。ChatGPT 的 API 调用会上传数据到 OpenAI 服务器。

3. **生产监控**：我们有完整的 Prometheus + Grafana 监控体系，可以实时看到查询成功率、响应时间、Badcase 趋势。ChatGPT 是黑盒，出问题后无法定位。

4. **结果可信**：我们有一致性校验机制，比如查询流量后会检查数值是否在合理范围内（0-10000 m³/s）。ChatGPT 可能编造数据（幻觉）。

所以我们的定位是**垂直领域的生产级 AI 助手**，而不是通用对话工具。"

### Q2: "你们的 RAG 准确率 87% 是怎么得到的？"

**回答思路**：

"我们建立了一个包含 100 个真实用户查询的测试集，评估方式如下：

1. **标注 Ground Truth**：人工标注每个查询应该返回哪些文档片段（Top 3）
2. **计算指标**：
   - 准确率 = 返回的文档中有用的比例
   - 召回率 = 应该返回的文档中找到的比例
3. **对比实验**：
   - 纯 FAISS：准确率 72%，召回率 68%
   - 纯 BM25：准确率 65%，召回率 71%
   - 混合 RRF：准确率 87%，召回率 85%

**具体案例**：
查询'暴雨强度怎么计算'：
- FAISS 找到 3 篇相关，但漏掉了一篇包含'IDF 曲线'关键词的核心文档（因为文档没用'计算'这个词）
- BM25 找到'IDF 曲线'那篇，但漏掉了用'推导''公式'等同义词的文档
- 混合后把两者结果合并，召回率从 60% 提升到 80%

所以我们的 87% 是基于真实测试集的，不是拍脑袋。而且我们会持续收集 Badcase 来优化这个指标。"

### Q3: "你们的监控体系解决了什么问题？"

**回答思路**：

"监控体系解决了**从 Demo 到生产**的关键问题：

1. **SLA 保障**：我们承诺 P95 响应时间 < 5s，工具成功率 > 95%。没有监控就无法证明我们达标，也无法在违反 SLA 时及时发现。

2. **快速定位故障**：假设用户反馈'查询很慢'，我们可以：
   - 看 Grafana：确认是全局慢（LLM 问题）还是个别查询慢（数据库问题）
   - 看 Prometheus：查看具体是哪个工具调用耗时长
   - 看数据库监控：是否连接数过多、查询被阻塞

   这个过程从'靠猜'变成'看数据'，定位时间从 1 小时降到 5 分钟。

3. **产品迭代依据**：
   - 通过'工具调用分布'饼图，发现 45% 查询是流量数据 → 优先优化流量查询性能
   - 通过'Badcase 趋势'，发现周五下午错误率高 → 调研后发现用户在赶周报，需求是'批量导出' → 开发新功能

4. **用户信任**：给客户演示时，打开 Grafana 实时看板，展示'查询成功率 96%''P95 响应 4.8s'，比口头承诺更有说服力。

所以监控不是为了'炫技'，而是**生产系统的必备基础设施**。"

### Q4: "如果 LLM 给出错误答案怎么办？"

**回答思路**：

"这是 AI 产品最大的挑战，我们有三层防护：

**第一层 - 一致性自校验**（防止明显错误）：
- Agent 查询流量后，会检查数值是否在 [0, 10000] m³/s 范围内
- 如果 LLM 说'流量 50000 m³/s'（明显超标），自动重试或标记为异常

**第二层 - 数据溯源**（让用户可验证）：
- 每个答案都附上数据来源，比如：
  ```
  棠荆河 TJ01 站 2024-08-15 14:00 流量 850 m³/s
  [数据来源] PostgreSQL 表: water_observation, 记录ID: 123456
  ```
- 用户可以点击跳转到原始数据，自己验证

**第三层 - Badcase 闭环**（持续优化）：
- 用户可以点'这个答案有问题'反馈
- 每个 Badcase 进入工单系统，产品经理分类（数据错误/理解错误/工具故障）
- 每周复盘 Top 10 Badcase，针对性优化

**实际效果**：
- 上线 2 个月，收到 37 个 Badcase
- 其中 18 个是数据缺失（不是 LLM 问题）→ 补充数据
- 12 个是意图识别错误 → 优化 Prompt
- 7 个是真幻觉 → 加入一致性校验规则

所以错误率从最初的 8% 降到现在的 4%，还在持续改进。"
