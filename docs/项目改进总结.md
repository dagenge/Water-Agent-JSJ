# 水文Agent项目改进总结

## 一、改进概述

本次改进将原有的"玩具级"水文Agent升级为"生产级"应用，主要从以下6个维度进行全面提升：

1. **数据库架构升级**：SQLite → PostgreSQL + pgvector
2. **监控系统建设**：Prometheus + Grafana 实时监控
3. **质量保障体系**：Badcase收集 + 迭代优化闭环
4. **工具协议标准化**：MCP Server实现跨团队复用
5. **版本管理**：A/B测试 + 灰度发布 + 回滚机制
6. **测试体系**：回归测试 + 准确率评估

## 二、技术改进详情

### 2.1 PostgreSQL + pgvector 数据层

**改进前（SQLite）的问题**：
- 单文件嵌入式数据库，不支持并发写入
- 向量存储在FAISS文件中，与元数据分离，一致性难保证
- 无法实现SQL条件过滤 + 向量检索的组合查询
- 单机部署，无法支撑多团队访问

**改进后（PostgreSQL + pgvector）**：
```python
# 配置文件: config/postgres/database.py
engine = create_engine(
    DATABASE_URL,
    poolclass=QueuePool,
    pool_size=10,              # 常驻连接数
    max_overflow=20,           # 峰值时额外连接数
    pool_pre_ping=True,        # 连接前检测有效性
    pool_recycle=3600,         # 1小时回收连接
)
```

**向量存储模型**：
```python
class KnowledgeDocument(Base):
    __tablename__ = "knowledge_documents"
    
    id = Column(Integer, primary_key=True)
    basin_id = Column(String(20))
    content = Column(Text, nullable=False)
    embedding = Column(Vector(384))  # pgvector类型
    
    # IVFFlat索引加速检索
    __table_args__ = (
        Index("idx_knowledge_embedding", "embedding", 
              postgresql_using="ivfflat", 
              postgresql_ops={"embedding": "vector_cosine_ops"}),
    )
```

**组合查询示例**：
```sql
-- 先用SQL过滤流域，再做向量检索
SELECT content, embedding <-> query_vector AS distance
FROM knowledge_documents
WHERE basin_id = 'hzk'  -- SQL条件过滤
ORDER BY embedding <-> query_vector  -- 向量相似度排序
LIMIT 5;
```

**性能提升**：
- 查询响应时间：5.14秒 → 2.94秒（-42.8%）
- P95延迟：优化32.6%
- 向量检索时间：800-1200ms → 200-400ms（-65%）

### 2.3 Badcase收集与迭代优化

**自动检测规则**：
```python
# monitoring/badcase_manager.py

class BadcaseDetector:
    @staticmethod
    def detect_from_session(session_data):
        issues = []
        
        # 1. 工具调用失败
        failed_tools = [tc for tc in tool_calls if not tc.get("success")]
        if failed_tools:
            issues.append({
                "category": "tool_failure",
                "reason": f"{len(failed_tools)}个工具调用失败",
                "confidence": 0.9
            })
        
        # 2. 一致性校验触发
        if session_data.get("is_corrected"):
            issues.append({
                "category": "result_interpretation",
                "reason": "一致性校验触发修正",
                "confidence": 0.8
            })
        
        # 3. 响应时间异常
        if execution_time > 60000:
            issues.append({
                "category": "timeout",
                "reason": f"响应时间过长: {execution_time/1000:.1f}秒",
                "confidence": 0.7
            })
        
        return max(issues, key=lambda x: x["confidence"])
```

**Badcase管理流程**：
```
1. 用户反馈/自动检测 → 记录到user_feedbacks表
2. 每周抽检50条 → 研究员人工标注
3. 分类标注（tool_selection/parameter_error/result_interpretation/knowledge_error）
4. 针对性修正（改prompt/调整工具/优化RAG）
5. 加入测试集 → 回归测试验证
6. 灰度上线 → 观察指标
```

### 5.3 常见追问及答案模板

**Q: 为什么不用MySQL？**
A: "考虑过MySQL，但PostgreSQL在向量支持上更成熟。pgvector是PostgreSQL的官方扩展，生态完善，文档丰富。MySQL 8.0.31+也有实验性向量类型，但生态不如pgvector成熟。而且PostgreSQL的JSON支持、全文检索、地理空间扩展（PostGIS）都更强，为后续功能扩展留有空间。"

**Q: 向量维度为什么是384？**
A: "使用的embedding模型是BGE-small-zh-v1.5，输出维度固定384。选这个模型是因为：1）中文语义理解好；2）模型小（133MB）推理快；3）在中文语义相似度任务上表现优秀。如果要更高精度，可以换BGE-large-zh（1024维），但推理时间会增加。"

**Q: 如果MCP Server挂了怎么办？**
A: "1）健康检查：下游团队定时调用health接口，超时或失败触发告警；2）重启机制：systemd配置自动重启；3）降级方案：下游团队缓存最近调用结果，MCP不可用时返回缓存数据并提示用户；4）备份服务：部署主备两个MCP Server实例，通过负载均衡切换。"

**Q: 准确率怎么评估的？**
A: "建立了8个场景的测试用例集，每个用例有expected_intent、expected_tools、expected_output_keywords。执行测试时，对比实际输出和期望输出，三者都匹配才算通过。准确率=通过用例数/总用例数。另外从真实用户反馈中抽样人工标注，计算准确率。两种方式结合，确保评估的可靠性。"
